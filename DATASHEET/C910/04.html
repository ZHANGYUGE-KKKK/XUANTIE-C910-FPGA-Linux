核心概念分支预测分支目标缓冲器预测错误惩罚

一条if语句就能让CPU的流水线“断流”。处理器取指时，遇到条件分支指令，不知道下一步该取哪条指令——是跳转还是不跳？等执行完分支条件再取指，流水线就得空转好几个周期。分支预测就是让CPU提前猜一个方向，赌对了流水线不停，赌错了就清空已经预取的指令，重新开始。

分支预测的代价：一个简单的对比

场景 流水线行为 浪费的周期（典型值）
无分支预测，每次等待分支结果 流水线停顿，直到分支条件算出 3~6个周期
静态预测（总是预测不跳转） 继续取顺序指令，猜错时冲刷流水线 猜对0个，猜错3~6个
动态预测（2位饱和计数器） 根据历史记录预测，命中率约85%~90% 平均不到1个周期

玄铁C906采用简单的静态预测策略，而C910使用动态预测加分支目标缓冲器（BTB）。这个差异直接决定了两个处理器在循环密集和分支密集代码上的性能差距。

分支预测器通常挂在取指阶段之后、译码阶段之前——当译码器识别出当前指令是条件分支时，预测器立刻给出“跳转”或“顺序执行”的判断，取指单元据此决定下一周期取哪里的指令。

静态预测：C906的选择

静态预测不依赖历史记录，仅凭指令本身的特性或编译器给出的提示做判断。玄铁C906采用“向后跳转预测为跳转，向前跳转预测为不跳转”的规则。

这个规则背后的直觉很简单：向后跳转通常是循环的末尾跳回开头，大概率会多次执行；向前跳转往往是if语句跳过一段代码，通常不执行。实际开发中，大部分循环体代码在C906上都能获得较好的预测命中率。

生活类比：红绿灯的固定模式

静态预测就像你每天走同一条路，知道某个红绿灯在早上8点总是绿灯。你不需要观察路口情况，直接按经验通过。如果某天红绿灯改了时间，你就会闯红灯。

技术定义：静态分支预测是处理器根据分支指令的偏移方向或编译器插入的静态提示（如RISC-V的B指令中的预测位），在无历史数据的情况下做出固定方向的预测。

我在调试C906的板子时遇到过一个问题：一个三层嵌套循环，内层循环只有3次迭代，但外层循环有1000次。由于C906的静态预测只能识别跳转方向，内层循环的最后一次跳转总是预测错误——因为循环结束时不跳转，而预测器认为向后跳转应该跳。这个场景下，预测命中率只有75%左右。如果换成C910的动态预测，几次迭代后就能学到“这个分支大部分时候跳转，只在最后一次不跳”，命中率可以提升到95%以上。

动态预测：C910的2位饱和计数器 + BTB

C910使用2位饱和计数器作为核心预测器。每个分支指令对应一个2位状态机，有4种状态：强不跳、弱不跳、弱跳转、强跳转。每次预测正确，状态向“强”方向移动一级；预测错误，向反方向移动一级。

这个状态机的好处是：对于“几乎总是跳转”或“几乎总是不跳转”的分支，需要连续两次预测错误才会改变预测方向，抗干扰能力强。对于“90%跳转”的分支，大部分时间处于强跳转状态，只有偶尔不跳转时才会降为弱跳转，但很快又会回到强跳转。

C910的BTB（分支目标缓冲器）存储了最近执行过的分支指令的PC地址和对应的目标地址。当取指单元取到一条指令时，同时查询BTB：如果命中，直接得到目标地址，不用等译码完成再计算。BTB通常有64~128个条目，采用直接映射或组相联结构。

常见误区

  • 误区1：认为动态预测一定比静态预测好。实际上，对于规律性极强的循环分支，静态预测的命中率也能超过90%，而且动态预测需要额外的硬件开销（存储器和状态机），在低功耗场景下C906的静态方案更合适。
  • 误区2：以为BTB存储的是预测方向。BTB只存目标地址，不存预测方向。预测方向由单独的2位饱和计数器或全局历史寄存器给出。BTB和预测器是两个独立的硬件模块。
  • 误区3：忽略预测错误后的流水线冲刷代价。C910的流水线深度比C906深，一次预测错误需要清空更多的预取指令，浪费的周期也更多（C910约8~10个周期，C906约4~6个周期）。所以C910虽然预测准确率高，但一旦猜错，代价更大。
编者提示：在实际SoC集成中，分支预测器的设计需要和缓存行预取器配合。C910的BTB命中后，会同时触发指令缓存的下一次预取，将目标地址之后的连续指令提前拉入缓存。如果BTB预测错了，不仅流水线要冲刷，预取的缓存行也可能作废，造成额外的内存带宽浪费。因此，玄铁团队在C910中加入了“预测确认”机制——在分支指令执行完毕、确认预测正确后，才真正提交预取的缓存行；如果预测错误，预取的数据直接丢弃，不污染缓存。这个细节在芯片验证阶段很容易被忽略，我曾在一次性能分析中看到L1指令缓存命中率异常低，排查了两天才发现是预取器在预测错误后没有正确丢弃无效数据。

玄铁C906与C910的分支预测对比

特性 C906 C910
预测策略 静态（向后跳/向前不跳） 动态（2位饱和计数器）
BTB 无 有，64~128条目
预测错误惩罚 约4~6个周期 约8~10个周期
典型命中率（循环代码） 70%~85% 90%~97%
硬件开销 几乎为零 数千门逻辑
适用场景 低功耗、实时控制 高性能计算、复杂控制流

从表中可以看出，C906放弃了BTB和动态预测器，换来了极低的功耗和面积。对于物联网传感器节点、电机控制等场景，分支数量少且规律性强，静态预测已经足够。而C910面向Linux、多媒体处理等场景，代码中充满了虚函数调用、switch-case、异常处理等难以静态预测的分支，动态预测带来的性能收益明显大于硬件开销。

适合C906的场景

  • 循环次数固定的for循环
  • 简单的if-else结构
  • 中断服务函数（分支极少）

适合C910的场景

  • 虚函数调用密集的C++代码
  • 状态机驱动的协议处理
  • 含有大量switch-case的解析器

两者都棘手的场景

  • 数据驱动的分支（如查表后跳转）
  • 随机性强的条件判断
  • 间接跳转（函数指针）

分支预测对程序员的影响

理解分支预测机制后，可以写出对处理器更友好的代码。核心原则是：让分支结果尽量有规律。

  • 将大概率执行的分支放在if中，小概率放在else中。虽然C910的动态预测能逐渐适应，但初始状态是“弱不跳转”，第一次执行时如果分支跳转了，就会预测错误。把大概率分支放在if中（不跳转），可以减少第一次预测错误的概率。
  • 减少循环内部的分支。一个循环内部如果有多个if-else，每个分支都会竞争BTB条目（C910的BTB只有64~128个），可能导致频繁的BTB替换，降低命中率。可以考虑将循环展开或使用查表代替分支。
  • 避免过于稀疏的switch-case。switch-case在RISC-V上通常被编译为跳转表，属于间接分支。C910的BTB对间接分支的支持有限（只有简单的目标地址缓存），如果case值分布很散，跳转表很大，BTB命中率会下降。

我在一个C910的项目中遇到过性能瓶颈：一个网络包解析函数，内部有一个switch-case，case值有200多个，但实际运行时只用到其中10个。由于BTB只有128个条目，这200多个目标地址频繁替换，BTB命中率只有30%左右。改成if-else链后，虽然代码长了，但BTB命中率提升到85%，整体吞吐量提高了40%。这就是分支预测对实际性能的影响。

动手试一试

找一块玄铁C906或C910的开发板（或者用QEMU模拟器），写一段包含条件分支的C代码，例如：

  • 一个循环1000次的for循环，内部有一个if(i % 2 == 0)的分支。
  • 先用默认编译选项运行，记录执行时间。
  • 然后用__builtin_expect提示编译器（如将if(i % 2 == 0)改为if(__builtin_expect(i % 2 == 0, 1))），再次运行并对比时间。
  • 观察C906和C910上的差异——C906上静态预测无法被编译器提示改变，所以时间变化不大；C910上动态预测会逐渐适应，时间可能有小幅改善。

提示：如果使用QEMU，可以用 -cpu c906 或 -cpu c910 参数切换处理器模型。

本章小结

  • 分支预测的目的是减少流水线因等待分支结果而产生的空闲周期。
  • C906使用静态预测（向后跳/向前不跳），硬件开销小，适合低功耗场景。
  • C910使用2位饱和计数器加BTB的动态预测，命中率高，适合复杂控制流的应用。
  • 预测错误需要冲刷流水线，C910的惩罚周期比C906大，但整体性能仍然优于静态预测。
  • 程序员可以通过调整分支规律性来提升预测命中率，从而获得更好的实际性能。
