性能计数器是处理器内部的一组专用寄存器，专门用来统计流水线中的各种事件——比如指令退休数、缓存缺失次数、分支预测错误次数。玄铁C906和C910都内置了性能监控单元（PMU），但C910的监控能力更强，还支持虚拟化场景下的Guest计数器。

生活类比：厨房里的计时器

想象你在厨房里做一道复杂的菜，你同时用三个计时器：一个记录总烹饪时间（时钟周期），一个记录切菜用了多久（指令退休），一个记录烤箱开关了多少次（缓存访问）。性能计数器就是处理器内部这些"计时器"，帮你搞清楚处理器的时间都花在了哪里。

性能事件的分类

实际开发中，大部分团队会优先关注以下几类事件：指令退休数（衡量程序执行了多少指令）、L1缓存缺失（衡量数据局部性）、分支误预测（衡量分支代码质量）。这三个指标基本能定位90%的性能瓶颈。

关键选择：监控什么事件？

  • 如果程序运行缓慢但指令数正常——查缓存缺失
  • 如果指令数异常高——查循环展开或内联问题
  • 如果分支误预测率高——查条件分支的分布模式

配置计数器：CSR操作

玄铁处理器通过一组专用的CSR（控制状态寄存器）来管理性能计数器。核心寄存器包括：

  • mcycle：记录自启动以来的时钟周期数（只读）
  • minstret：记录自启动以来的指令退休数（只读）
  • mhpmcounter3 ~ mhpmcounterN：通用硬件计数器，可配置监控事件
  • mhpmevent3 ~ mhpmeventN：对应计数器的事件选择寄存器，写入事件ID

配置步骤很简单：先向mhpmeventX写入事件ID，再使能该计数器。C906和C910的事件ID不同，需要查阅对应数据手册。

常见误区

  • 误区1：认为所有性能计数器默认都是使能的——实际上，通用计数器需要手动使能，只读的mcycle/minstret始终在运行。
  • 误区2：配置事件ID后立即读取计数器——需要等待几个时钟周期让硬件同步，否则读到的可能是旧值。
  • 误区3：在中断处理函数中读取计数器——中断可能打断流水线计数，导致值偏大或偏小，应该在外层代码中读取。

溢出中断与采样

当计数器达到预设的阈值时，可以触发溢出中断。这个功能在性能采样中非常有用——你可以设置计数器每N个事件触发一次中断，在中断服务程序中记录当前的PC值，从而生成程序的"热点分布图"。

我在项目中踩过这个坑：一开始把溢出阈值设得太低（比如100次缓存缺失），结果中断频率极高，反而拖慢了被监控的程序。后来调整为每10000次缺失中断一次，采样密度刚刚好，既能定位热点又不影响程序行为。

编者提示：溢出中断的阈值设置需要考虑监控时间窗口。如果程序运行时间很短（微秒级），阈值设小一些；如果程序运行时间长（秒级），阈值可以设大一些。一个经验做法是：先预估事件总数，然后让中断次数在100-500次之间。比如预估指令退休数为1亿，那么阈值可以设为20万~100万。

监控单元的内部实现

玄铁处理器的监控单元位于流水线的提交阶段（Commit Stage）。当指令退休时，监控单元会检查该指令是否触发了配置的事件（比如L1缓存缺失），如果匹配，就递增对应的计数器。

C910的监控单元做了增强：它支持事件过滤器，可以按特权模式（M/S/U）或虚拟化模式（Host/Guest）筛选事件。举个例子，你可以只统计用户态程序发生的缓存缺失，忽略内核态的影响。这个功能在分析应用程序性能时特别有用。

应用场景1：编译器优化

  • 监控分支误预测率
  • 调整分支预测提示
  • 对比优化前后的CPI

应用场景2：缓存调优

  • 监控L1缺失率
  • 调整数据布局
  • 验证预取效果

应用场景3：系统级分析

  • 监控总线带宽
  • 定位多核冲突
  • 评估功耗策略

应用场景4：实时系统

  • 监控中断延迟
  • 检测WCET超限
  • 验证任务隔离

读取计数器的实际代码

下面是一段在C906上读取性能计数器的示例（使用内联汇编）：

// 读取mcycle（时钟周期数）
unsigned long long read_cycles() {
    unsigned long lo, hi;
    asm volatile("rdcycleh %0\n"
                 "rdcycle  %1\n"
                 : "=r"(hi), "=r"(lo));
    return ((unsigned long long)hi << 32) | lo;
}

// 配置计数器3监控L1数据缓存缺失（事件ID假设为0x12）
void config_counter3() {
    asm volatile("csrw mhpmevent3, %0\n" :: "r"(0x12));
    // 使能计数器3（假设mcountinhibit寄存器bit3清零表示使能）
    unsigned long inhibit;
    asm volatile("csrr %0, mcountinhibit\n" : "=r"(inhibit));
    inhibit &= ~(1UL << 3);
    asm volatile("csrw mcountinhibit, %0\n" :: "r"(inhibit));
}

注意：rdcycleh和rdcycle是RISC-V标准指令，分别读取mcycle的高32位和低32位。mcountinhibit寄存器的bit0控制mcycle，bit1控制minstret，bit3~bitN控制对应的通用计数器——清零表示使能，置1表示暂停。

如果你看到计数器读出来一直是0，大概率是mcountinhibit没有正确配置——默认情况下通用计数器是禁用的，需要显式使能。还有一个隐藏的坑：在S-mode下如果mcounteren寄存器没有开放权限，读取mcycle/minstret会触发非法指令异常。

性能数据的解读思路

拿到计数器数值后，怎么分析？最常用的指标是CPI（Cycles Per Instruction），即每条指令平均周期数。计算公式很简单：

CPI = 总时钟周期数 ÷ 指令退休数

理想情况下CPI接近1.0，但实际中由于缓存缺失、分支误预测、数据依赖等因素，CPI通常在1.5~3.0之间。如果你测出的CPI超过3.0，说明程序有严重的流水线停顿。

排错线索

  • CPI > 3.0且L1缓存缺失率高 → 优化数据局部性
  • CPI > 3.0且分支误预测率高 → 简化条件逻辑或使用查表法
  • CPI > 3.0但两者都正常 → 检查TLB缺失或总线竞争

C906与C910的差异点

除了计数器数量和位宽不同，还有两个关键差异：

  • 事件ID范围：C906的事件ID从0x00到0x27（约40个），C910扩展到0x00到0x3B（约60个），新增了向量单元事件和虚拟化相关事件。
  • 溢出中断机制：C906的溢出中断统一路由到机器定时器中断，C910则使用独立的性能监控中断（属于平台中断控制器），响应速度更快。

本章小结

  • 性能计数器是处理器内部的事件统计硬件，用于定位性能瓶颈。
  • C906提供6个通用计数器，C910提供8个，支持溢出中断和事件过滤。
  • 配置流程：选择事件ID → 写入mhpmeventX → 使能计数器（清零mcountinhibit对应bit）。
  • CPI是衡量流水线效率的核心指标，理想值接近1.0。
  • 溢出中断可用于性能采样，阈值设置需平衡采样密度与开销。
