8.1 多核场景下的数据"打架"问题

Core 0
⇄
L1 Cache
⇄
共享内存
↗↘
Core 1
⇄
L1 Cache
⇄
共享内存

假设一个最简单的场景：两个核心同时访问内存地址0x1000处的变量。Core 0把值从0改成了1，但数据只写入了自己的L1 Cache，还没来得及写回共享内存。此时Core 1去读同一个地址，拿到的是旧值0——两个核心看到的数据不一致，程序逻辑立刻崩溃。

缓存一致性
生活类比：你和你室友各有一份冰箱里的牛奶记录单。你喝完牛奶划掉了记录，但室友的记录单上还显示有牛奶——他拿着空瓶子去倒，结果啥也没有。多核一致性就是保证所有核心的"记录单"实时同步，不出现这种乌龙。
技术定义：在多核处理器系统中，每个核心的私有缓存（L1/L2）与共享内存之间，以及不同核心的私有缓存之间，对同一内存地址的数据内容保持一致。

玄铁C906和C910都是多核处理器。C906最多支持4核，C910最多支持4核（部分配置可达8核）。核数越多，数据打架的风险越大。解决这个问题的核心方案就是缓存一致性协议。

8.2 监听协议：核心间的"广播通知"

玄铁C906和C910采用的是监听协议（Snooping Protocol），这是多核一致性中最直观的方案。每个核心的缓存控制器会监听总线上的所有内存访问请求。

监听协议核心机制
核心操作总线广播内容其他核心的响应
Core 0 读某个地址"我要读地址X"如果有修改过的数据，必须写回共享内存或直接转发给Core 0
Core 0 写某个地址"我要写地址X"如果其他核心的缓存中有该地址的副本，必须作废（Invalidate）
Core 0 写回内存"地址X的数据已更新"其他核心的缓存中该地址标记为失效

我在项目中调试C910的4核系统时，遇到过一个问题：一个核修改了共享变量，另一个核读到的还是旧值。排查了半天，发现是软件没有使用原子操作指令（AMO指令），直接用了普通store指令。普通store指令只通知了总线，但软件层面没有做内存屏障（fence），导致其他核的缓存没有及时收到作废信号。这个问题在玄铁平台上有一个明显的特征——用逻辑分析仪抓总线，能看到写请求广播了，但对应核心的缓存控制器没有响应作废确认。

关键理解
  • 监听协议的核心是"每次内存访问都通知所有人"，因此总线带宽会成为瓶颈——核心数越多，广播流量越大。
  • C906和C910在硬件层面自动处理监听和作废，但软件必须配合使用原子操作和内存屏障指令（fence.i / fence）来保证顺序。

8.3 MESI协议：缓存行的四种状态

MESI协议
生活类比：图书馆里一本书有四种状态——你手里正在看（Modified）、你手里在看但别人也有副本（Shared）、只有你一个人借了这本书（Exclusive）、书已经还回去了不在任何人手里（Invalid）。图书馆管理员（总线）根据状态决定要不要通知其他人。
技术定义：每个缓存行（Cache Line）维护一个状态机，状态包括Modified（已修改）、Exclusive（独占）、Shared（共享）、Invalid（失效），协议通过状态转换保证一致性。

玄铁C906和C910的L1 Cache和L2 Cache都实现了MESI协议。每个缓存行占用2个状态位。下面这个表格展示了核心的状态转换规则：

MESI状态转换表（核心视角）
当前状态本地读本地写其他核心读其他核心写
Modified (M)直接读缓存直接写缓存写回内存，转为Shared写回内存，转为Invalid
Exclusive (E)直接读缓存直接写缓存，转为Modified转为Shared转为Invalid
Shared (S)直接读缓存广播写请求，转为Modified保持Shared转为Invalid
Invalid (I)从内存或其他核获取数据从内存或其他核获取数据，写后转为Modified保持Invalid保持Invalid

实际开发中，大部分团队会选择在启动阶段将所有核心的L1 Cache初始化成Invalid状态，然后通过硬件自动管理状态转换。如果某个核心长时间独占一个缓存行（Exclusive状态），其他核心读这个地址时会触发总线事务，状态自动降级为Shared。

常见误区

  • 误区1：认为MESI协议能自动解决所有数据一致性问题。实际上，MESI只保证缓存行级别的数据一致性，不保证不同核心对同一个缓存行内不同字段的写操作顺序——这需要软件用原子操作或锁来保证。
  • 误区2：在C906上写多核程序时，忘了加fence指令。玄铁C906的硬件不会自动插入内存屏障，如果两个核心通过共享内存通信，必须显式使用fence指令保证写操作的可见性。
  • 误区3：把非对齐访问的数据放在同一个缓存行中。MESI协议以缓存行（通常64字节）为单位管理状态，如果两个核心频繁修改同一缓存行中的不同字段，会产生大量总线广播（伪共享），性能急剧下降。

8.4 玄铁平台的一致性实现细节

C906和C910在缓存一致性上有一个关键差异：C906的L1 Cache是写直达（Write-Through）策略，每次写操作都会穿透到L2 Cache；C910的L1 Cache是写回（Write-Back）策略，写操作先留在L1 Cache，直到缓存行被替换时再写回L2或内存。

Core 0
↕
L1 Cache (Write-Through C906 / Write-Back C910)
↕
L2 Cache (统一缓存，支持MESI监听)
↕
总线接口单元(BIU)
→
共享内存/外设

写直达策略的优势是一致性实现简单——每次写操作都会通知总线，其他核心的缓存立即作废。缺点是写性能差，每次写都要访问L2 Cache。写回策略的写性能好，但需要更复杂的监听逻辑，因为修改后的数据可能只存在于L1 Cache中，其他核心读这个地址时，必须从L1 Cache中获取最新数据。

编者提示：在C906上做多核开发时，如果你发现某个核心的写操作特别慢，检查一下是不是频繁写同一个缓存行。因为写直达策略下，每次写都会触发L2 Cache的写操作和总线广播。一个优化技巧是：把频繁写的数据集中到一个缓存行中，让总线广播一次覆盖多个写操作，而不是每个写操作都单独广播。另外，C906的L1 Cache大小是32KB（指令+数据各32KB），缓存行大小是64字节，了解这些参数有助于你设计数据结构时避免伪共享。

8.5 多核编程的软件配合

硬件协议只解决了"数据在缓存间怎么同步"，但多核程序还需要软件层面的配合。玄铁平台提供了以下机制：

原子操作指令

  • AMOSWAP、AMOADD等RISC-V原子操作
  • 保证读-修改-写操作的原子性
  • 硬件自动加锁，总线不会被打断

内存屏障指令

  • fence：保证前后访存操作的顺序
  • fence.i：保证指令缓存与数据缓存一致
  • 软件必须显式调用，硬件不自动插入

自旋锁实现

  • 基于AMOSWAP实现锁变量
  • 锁变量放在独立的缓存行中
  • 避免锁竞争时的伪共享

缓存刷新指令

  • C906/C910支持dcache.cpa等指令
  • 强制将脏缓存行写回内存
  • 用于DMA传输前后的数据同步

举个实际例子：在C910上实现两个核心之间的消息队列。发送端核心写队列后，必须先执行fence指令确保写操作对总线可见，再写一个"数据就绪"标志位。接收端核心读到标志位后，也要先执行fence指令，再读队列数据。如果少了这个fence，接收端可能读到旧数据。

我在调试一个C906的4核系统时，遇到过这样一个问题：三个核心同时更新一个全局计数器，程序跑了几分钟后计数器的值莫名其妙地少了。用示波器抓总线，发现AMOADD指令没有被正确序列化——原因是编译器优化把AMOADD指令重排序到了循环体外面。解决办法是在计数器更新前后加volatile关键字和fence指令，强制编译器不优化。

动手试一试

在玄铁C906或C910的开发板上运行以下实验：

  1. 编写一个简单的多核程序：两个核心各自对一个共享变量累加100万次，使用普通store指令（不加fence和原子操作），观察最终结果是否等于200万。
  2. 修改程序，使用AMOADD指令替代普通store，再跑一次，对比结果和运行时间。
  3. 在共享变量前后各填充64字节的padding（使其独占一个缓存行），再跑一次，观察性能变化。

实验工具：可使用玄铁官方SDK中的GCC工具链编译，用OpenOCD+GDB调试多核程序。

检验你的理解

  1. 判断题：MESI协议中，一个缓存行处于Exclusive状态时，其他核心的缓存中一定没有该缓存行的副本。（对/错）
  2. 选择题：在玄铁C906上，两个核心通过共享内存通信，发送端写完数据后必须执行哪条指令才能保证接收端看到最新数据？A. fence B. AMOSWAP C. ecall D. 不需要任何指令
  3. 判断题：写回策略比写直达策略的一致性实现更简单，因为写操作不需要通知总线。（对/错）

本章小结

  • 多核一致性解决的是"不同核心的私有缓存中同一地址的数据不一致"的问题，玄铁C906/C910采用监听协议+MESI状态机实现硬件一致性。
  • MESI协议定义了缓存行的四种状态（Modified、Exclusive、Shared、Invalid），状态转换由总线监听事件驱动。
  • C906使用写直达策略（写操作穿透到L2 Cache），C910使用写回策略（写操作留在L1 Cache），两种策略在一致性和性能上有不同权衡。
  • 硬件一致性协议不能替代软件层面的原子操作和内存屏障指令，多核编程时必须显式使用fence和AMO指令。
  • 伪共享（多个核心频繁修改同一缓存行中的不同字段）是多核性能杀手，通过数据对齐和填充可以避免。
